# Jump to Race Start from the session record

> **Issue:** [#1354](https://github.com/niklam/iracedeck/issues/1354) · **Supersedes:** _none_ · **Superseded by:** _none_
>
> Point-in-time design record. The code and `.claude/rules/` are the truth; this is not documentation.

This builds on the per-session replay store (#1162) and the lap record (#1203, landing fix #1275). The sim facts settled there are not restated here: live frames are `ReplayFrameNumEnd`, a saved `.rpy` keeps the live `SubSessionID` and lands live-recorded frames about a second early, offline sessions are held in memory only, and nothing may follow a seek until `ReplayFrameNum` reads the target.

## The decision

1. **The race goes green at one frame, and iRaceDeck records it live.** A new translator diff publishes `replay.greenFlag` when a race session leaves a real pre-green state for `Racing`, and on every caution restart. The per-session replay store (`@iracedeck/replay-store`, its own package since #1367) keeps those moments in a new `greens` section of the per-session file.
2. **Jump to Race Start is a lookup first.** The press resolves the target race session, finds its recorded start, and makes one waited jump to five seconds before the green, then plays. It switches no camera: the green belongs to the whole field, and the user has already chosen which car to watch.
3. **The fallback is the pole car's lap 1.** With no green record, the press jumps to five seconds before the pole car starts lap 1. That frame comes from the lap record when there is one, and from the #1203 walk otherwise. The result is close to the green, and before it except in the edge cases listed below.
4. **Restarts are recorded but not yet jumped to.** The one key ships for the race start, which is what the request says. **Its name says so (Niklas, 2026-10-14, after testing the press):** designed and built as Jump to Green Flag, which read as if it went to every green, the mode is **Jump to Race Start**: stored value `jump-to-race-start` (nothing had shipped, so the value moved with the label, on the key and the dial slot alike), key title `RACE START`, hold preview `START`. The sim's own vocabulary keeps its name, because it is about the green as an event and holds restarts too: the `replay.greenFlag` event, the `greens` section and the `replay-greens` recorder, and `green-flag-target`. Restarts go into the file from day one, because a replay's restarts cannot be recorded after the fact. A Next Green / Previous Green pair is the designed extension, for a later issue if it is ever asked for (see _Restarts_ below).

## What "the green" is

### Race start: `SessionState` entering `Racing` from a real pre-green state

The translator already treats `SessionState` as the authority on whether a race has started. `isPreGreen` in `iracing-sdk` is `GetInCar | Warmup | ParadeLaps` (plus `Invalid`). The fresh-connect briefing treats `Racing` in a race session as "too late" for the same reason. The pace-laps diff records that on a 1-lap rolling formation "the green flies at the line / `SessionState` flips to `Racing`". So the race start is **the first eligible tick of a race session on which `SessionState` reads `Racing`, when the previous eligible tick read `GetInCar`, `Warmup` or `ParadeLaps`.**

- **`Invalid` is not a pre-green state for this edge**, although `isPreGreen` counts it. An `Invalid → Racing` step is what a reconnect or a session-YAML reload mid-race looks like. Recording it would put a mid-race frame in the file as the start. So the diff uses its own three-state set and does not call `isPreGreen`.
- **One start per session instance; the latest one wins.** A re-grid re-enters `ParadeLaps`, and the rolling-start diff already treats that as a fresh edge. Its green is the real start, so a second start entry for the same `(sessionNum, sessionUniqueId)` replaces the first.
- **Race sessions only**: the session YAML's `SessionType` for the tick's `SessionNum` is exactly `Race`, read through the translator's `resolveSessionType`. Practice and qualifying also show `Racing` and a green bit, but a green there is not a start anyone reviews. A `Warmup` session goes green too and is not a race, which is why this is not the Race Engineer's "anything that is not practice or qualifying". A session whose type is not known yet (the YAML not parsed) records nothing. Heat sessions are assumed to report `Race` like any other (maintainer, 2026-10-12); the action's target rule reads the same field, so a session a press targets is one the record can hold.

**Rejected: a flag-bit edge (`StartGo` for standing starts, `Green` for rolling ones).** The flag diff's comments show how much the bits need to be told apart. `StartGo` also rises on every caution restart, `Green` rises under a yellow-checkered finish, and a green can lead `StartGo` by a tick. The start-light and flag diffs handle all of that with the caution phase, which is post-guard state. `SessionState` has a single meaning here and needs none of it. Timing is not the issue either way: a few ticks between the state flip and the bit are small against a five-second lead-in. **The capture that confirms the model:** on one standing and one rolling start, the diff's debug line on the edge tick logs `SessionFlags`. The offset to the `StartGo` (standing) or `Green` (rolling) rising edge must be a few ticks at most. If `Racing` trails the green by more than a second on either start type, the start edge moves to the first of the state flip and the start bit within the race session, and this spec is amended.

**Measured, 2026-10-12, on the 2026-09 watch captures:** the offset is zero ticks on both start types. The standing start (road course, 2026-09-18) goes `Warmup → Racing` with `StartGo` and `Green` rising in the same record of the watch, session tick 3603 at 56.98 s, and never passes through `ParadeLaps`. The rolling start (oval, 2026-09-17) goes `ParadeLaps → Racing` with both bits rising on the same record, at 201.18 s. Both are fixtures replayed through the diff in `replay-greens.captures.test.ts`. The captures carry no replay frame and no session YAML, so the frame the sim reports on that tick and where a jump to it lands are still the manual test's to measure.

### Restart: the green that ends a full-course caution

A restart is **a `Green` rising edge on an eligible tick of a race session in `Racing`, with neither `Caution` nor `CautionWaving` set on that tick, after an eligible tick in the same session on which one of them was set.** This is the definition `caution.restarted` documents, and a green rising with `Caution` still set (a yellow-checkered tick) is not one. The predicate is shared with `diff/caution.ts`, not copied. The "a caution is out" latch is the recorder's own, because the caution phase it would otherwise read is wiped on every replay tick. A latch cleared by an ineligible window simply misses that restart: an absent entry, never a wrong one.

**As built, the latch lives only while a caution bit is set:** it says whether `Caution` or `CautionWaving` was set on the previous eligible tick of this session, so a restart is the green rising on the very tick the caution bits drop. That is what `caution.restarted` announces, and it is what all three captured restarts show (two on the oval of 2026-09-17, one on the road course of 2026-09-18; the test asserts the count, so it cannot pass on a capture without restarts). The orderings nobody has measured, the bits dropping a tick before or after the green rises, record nothing. A latch left standing past the caution would catch them, at the cost of having to be cleared by something other than the flags, and is not built.

**A tick is one edge at most, and the start wins.** A green rising on the tick the state enters `Racing` is the start's own green, whatever the flags read on the formation lap.

A restart after a red flag is recorded only if iRacing raises a caution bit between the red and the green. That is not designed for; see _Out of scope_.

## Detection, in the translator

`packages/sim-events-iracing/src/diff/replay-greens.ts`, with its state in `TranslatorState`. It runs **before** the replay guard, next to `diffReplayLaps`, for the reason `replay-laps.ts` gives: the guard's early return would stop it on exactly the ticks where it has to notice it cannot see. Its state is left in `wipeStateForReplay`'s wiped set, because a re-seed is what returning from a replay needs.

- **The same gate as the lap record.** A tick is eligible when it is not in a replay, `SessionNum >= 0` and a frame is readable. "Not in a replay" is the translator's `inReplay`, the controller's debounced replay state (#1324): false only once `IsReplayPlaying` has read false for the exit grace, and never in a saved replay. Every ineligible tick marks the recorder unseeded and drops the caution latch, and the first eligible tick after that re-seeds without emitting. A driver who sat in the garage through the green (where iRacing reports `IsReplayPlaying: true`) therefore gets no start entry and the press falls back. The eligibility check is extracted from `replay-laps.ts` into one function both diffs call (`resolveReplayRecordTick` in `diff/replay-record-gate.ts`), so the two records can never disagree about which ticks are live.
- **`frame` is `resolveReplayFrame(telemetry)` on the edge tick**: `ReplayFrameNumEnd` under that gate, recorded raw like a lap start (#1162: no lag correction).
- **`sessionTimeMs` is `SessionTime` on the same tick**, in whole milliseconds. Nothing reads it in this design. It is stored because it is the one frame-free coordinate of the moment: a reader of the file can check a frame against it, and a later `ReplaySearchSessionTime` path would need no format change. It costs eight bytes per green.
- **A session change** (`SessionNum` or `SessionUniqueID` moves) re-seeds, and the caution latch is read afresh from the new session's flags.
- **#1324 exposure: closed by the gate.** `IsReplayPlaying` reads false for about 300 ms after every replay seek, and when this spec was written the gate read that raw flag, so it opened briefly during replay review. #1324 has since given the controller a debounced replay state and moved the lap record's gate onto it, and this diff shares that gate: a seek's blip tick is not eligible, so it can neither seed nor forge an edge. Whether session-level telemetry (`SessionState`, `SessionFlags`) follows the replay cursor during an in-session replay is still not measured (the per-car arrays read the live field, 2026-09-29, #1281), but nothing here depends on the answer any more.

### The event

```typescript
"replay.greenFlag": SimEvent<
  "replay.greenFlag",
  {
    /** `WeekendInfo.SubSessionID`; 0 for an offline session. */
    subSessionId: number;
    sessionNum: number;
    sessionUniqueId: number;
    /** The race start, or the green that ends a full-course caution. */
    kind: "start" | "restart";
    /** The live replay frame on the green tick, recorded raw. */
    frame: number;
    /** `SessionTime` on the same tick, whole milliseconds. */
    sessionTimeMs: number;
  }
>;
```

The green flag is a racing idea, not an iRacing one, so the event fits the sim-agnostic catalog the same way the lap events do. Whether it should be one event with a `kind` or two events: one, because the store treats both the same way and a consumer that only wants starts filters on one field. The scenario harness gets an `event-names.ts` entry. No callout uses it, so there is no shortcut button.

**Rejected: subscribe the store to the existing `caution.restarted` / `startLight.start-go.raised` / `flag.green.raised`.** Those events are shaped for the Race Engineer: suppressed while another family owns the moment, standing-only or in-car-only, and post-guard. Recording from them would tie the replay record to audio decisions. For example, `flag.green.raised` is deliberately silent on a rolling start's green when `StartGo` is up. They also carry no frame.

## The `greens` section

```json
"greens": {
  "version": 1,
  "sessions": [
    {
      "sessionNum": 2,
      "sessionUniqueId": 4,
      "greens": [
        { "kind": "start", "frame": 30215, "sessionTimeMs": 512433 },
        { "kind": "restart", "frame": 71904, "sessionTimeMs": 1199870 }
      ]
    }
  ]
}
```

Entries are kept in frame order, with at most one `start` per session (latest wins, as above). Restarts are de-duplicated by frame within the store's existing 60-frame marker window, so a tick-level double emit cannot create two entries.

**Lookup** (`greens.findGreen({ subSessionId, sessionNum, sessionUniqueId?, kind: "start" })`) follows the laps rule, with one difference for a press that names no instance. A query that carries a `sessionUniqueId` (a press made inside a race) is answered from that instance only: the session recorded under the pair either has a start or the lookup misses with `no green`, and when no session is recorded under the pair, the one other session with that `sessionNum` that has a start is taken, for a file whose unique ids did not survive the save; with several, the lookup misses with `no session`. A query that carries none (a press from practice or qualifying) takes the session with that `sessionNum` whose start has the highest frame, the latest instance in the recording. As first built, a named instance without a start fell through to that latest start too, which sent a press inside one pass of a restarted race into another; the code review caught it (2026-10-12).

**In the offline record the ids are exact.** The "one other session" rule above exists for a file read in a later sim run, which numbers the replay's sessions afresh. The offline record (`SubSessionID` 0) is never written and is dropped on disconnect, so everything in it was recorded in the sim run the query comes from, and it is also the only kind of record that can hold several instances of one `SessionNum`. There a session instance the record does not hold is a pass of a restarted AI event whose green was not seen, and the one other instance is another race: a named instance is answered from that instance or not at all. The store asks both lookups for this, the green's and the lap record's, because the fallback's own lap lookup would otherwise land the press in the earlier pass one step later (second read, 2026-10-12). Jump to Fastest Lap gets the same answer in an offline session, which is a correction there too. A miss carries the reason the action logs: `no file`, `no session`, `no green`, `newer format`.

**The record is fed from the bus.** `plugin-runtime`'s settings phase, which already subscribes the store to `replay.lapStarted` and `replay.lapTimed`, subscribes it to `replay.greenFlag` and calls `greens.record`. Neither the translator nor the store knows the other.

**The write path is the store's**: the debounce, the atomic replace, the flush on session change and exit. It also follows the unreadable-file merge. When a file that could not be read becomes readable, the in-memory greens merge into it: the file's start entry stays where both have one, and restarts are a union under the de-dupe rule.

### Compatibility of the persisted file

The replay file is persisted user data, so this is a contract change, and it is additive only.

- **The envelope does not move.** `REPLAY_FILE_VERSION` stays as it is, and `greens` is a new section with its own `version: 1`, like `laps`.
- **Older builds (3.4, 3.5) carry `greens` through untouched.** The store preserves every section it does not read on every write. A file opened alternately by 3.5 and 3.6 loses nothing.
- **This build reads older files.** A file with no `greens` section is a miss with reason `no green`, and the press falls back to the lap record, which those files have.
- **Newer builds' sections are carried through, not written.** A `greens` section whose `version` is above this build's is treated like a newer `laps` section: carried through verbatim, `record` returns false with one warning, and `findGreen` misses with `newer format`. An entry with an unknown `kind` and any unknown field on an entry or a session are kept on write (index signatures) and ignored by the lookup. What makes something an entry in version 1 is a `kind` and a finite `frame`, the key the list is ordered by, and a session is a finite `sessionNum` and `sessionUniqueId`; anything short of that is dropped on load, as the lap record drops what is not a lap. A later build that needs an entry without a frame has changed the shape, and raises `version`, which this build carries through whole.

## Which session the press targets

1. **The cursor's session, if it is a race.** That is `SessionNum` and `SessionUniqueID` from the replay's telemetry, classified by the `SessionType` of the `SessionInfo.Sessions` entry whose `SessionNum` field matches (not by array position), with the recorder's strict reading: exactly `Race`. In a heat-race event, pressing inside a heat goes to that heat's green.
2. **Otherwise the last race session in `SessionInfo.Sessions`.** In a single-race event, this is the race whether the cursor is in practice, qualifying or a warmup. In a heat-race event it is the feature, which is the one a reviewer is most likely after. No `sessionUniqueId` is known for it, so the lookup goes by `sessionNum`.
3. **No race session at all**: the press does nothing, and the key shows Replay Markers' unavailable look (grey colour slots, faded artwork). This is the only case that greys the key, and it is judged from the session list alone, so the key redraws when a replay of another session is opened. With no session list at all (not connected, the YAML not parsed yet) the key keeps its plain look: grey whenever the sim is closed would read as broken. A missing record does not grey it either, because the fallback can still land. From the car the key does not grey either: it does nothing, as every other Replay Control jump does there, and a key that is grey all race would read as broken.

The other press guards are the ones Jump to Fastest Lap uses, in the same order. `SessionNum < 0` (the post-seek transient) ignores the press. A press while a fastest-lap walk, a record jump or another green jump is in flight is ignored before any command is sent, through the same in-flight slot. Outside a replay nothing is sent, because iRacing ignores replay commands from the car; like Jump to Fastest Lap since #1324, that reads the controller's debounced replay state, not the raw `IsReplayPlaying`, which is false for about 300 ms after every seek.

**Session restarts in an offline AI event** (maintainer, 2026-10-12). An AI event can be restarted as a whole, so one recording can run Practice, Qualifying, Race and then Practice, Qualifying or the start of the Race again; hosted and official sessions never do. Each pass is its own `SessionUniqueID` under a `SessionNum` seen before, which is why the record is keyed by the pair: three race passes are three starts, and none replaces another. A press inside one pass goes to that pass's green (rule 1 carries the pair), and never to another pass's: when that pass's green was not recorded, the lookup misses and the fallback runs inside the pass. A press from outside any race (rule 2) knows no unique id, and takes the latest recorded start for that `SessionNum`, the one with the highest frame.

## The jump

**On a record hit:** the waited jump from `shared/replay-seek.ts` (#1275) to `max(0, frame − GREEN_APPROACH_FRAMES)`, holding the replay-cursor claim, then the playback step. `GREEN_APPROACH_FRAMES` is 300 (five seconds at 60 frames per second):

- **Standing start:** about the moment the gantry reaches Set, so the lights going out is in view.
- **Rolling start or restart:** the field bunched and approaching the line or restart zone.
- **Saved file:** the frame lag makes it about six seconds, which is still before the green.

Fastest Lap's 60 frames show a car crossing a line. Here the run-up is the point, which a single second does not show. It is a constant, not a setting. If the manual test shows the run-up is too short or too long, it is changed in one commit.

**Playback** is whatever the shared jump sequence applies. #1276 merges first (agreed between the two sessions, 2026-10-12), so the mode is written against its sequence: the press starts a replay jump before any command, the jump lands through the shared pause, seek and landing wait, and the **Replay jump playback** setting decides whether the replay then keeps the speed it had, plays at 1× or stays paused. The mode never sends a play command of its own, and the setting's list of covered jumps gains this one.

**On a miss:** the log line `Jump to race start: record MISS (<reason>); falling back to lap 1 of the pole car`, and then the fallback.

## The fallback: the pole car's lap 1

- **The car:** the pole sitter from `QualifyResultsInfo.Results` (`Position` 0), read through `grid-utils`. iRacing publishes that grid for standing and rolling starts alike, including race-only events (#974). With no grid, the fallback uses the car the camera is on. So it does when the target session's results list cars and the pole sitter is not among them (a heat it is not in, a car that never started): a search for a lap that car never drove would run to the end of the session and stop there. A session that lists no results yet cannot say who took part, and keeps the pole sitter.
- **The frame:** `laps.findLapStart` for that car's lap 1 in the target session. Replays recorded by 3.4 and 3.5 have a lap record and no green record, so this is a single jump for them. With no lap record, it runs the #1203 walk to lap 1 of that car in the target session. That requires the walk to take a target session other than the cursor's. As built, the walk is told which instance of the `SessionNum` to work in: the one the cursor is in (Jump to Fastest Lap, and a green press made inside the race), or the latest one in its session map (a green press from practice or qualifying, which knows no `SessionUniqueID` for the race). For that second kind the walk builds its session map afresh on every press: the cached map is keyed by the cursor's own session, and says nothing about a race that started, or was restarted, after it was built. When the recording holds no instance of the target session at all, which is a live event whose session list names a race it has not reached, the walk undoes itself: it puts the cursor back on the frame the press found it on and gives the replay the speed it had there, so the press leaves the replay as if it had not been made. The **Replay jump playback** setting is not applied, since nothing was jumped to. The key is not grey in that case, because nothing the plugin reads says whether a listed session has been run, so every such press still costs the few seconds the search takes to map the recording. The same undo ends a search whose map ran out of steps: the walk maps at most eleven session instances, and with more than that it cannot know which is the latest, so it refuses instead of taking the last race it reached. A converged walk records its landing in the lap record, as it already does, so the next press is a lookup.
- **On lap 0, only a lap search places the cursor.** A car can stand within a few metres of the line for minutes on lap 0, on its grid slot or in its pit stall, so a bisection probe that lands there reads as "at the end of the lap" on a frame that may be anywhere in the wait. Whether a gridded car reads lap 0 near 100 % is not measured, and the walk does not depend on it: when its target is lap 1 and no Next Lap or Previous Lap has moved the cursor yet, it sends one whatever the distance reads, and only a landing one of iRacing's own lap searches produced counts, verified or not. This holds for Jump to Fastest Lap as well when the fastest lap is lap 1.
- **A walk that could not verify its landing** still anchors the jump when the landed sample shows the car in the target session, on the lap before lap 1, in the last tenth of that lap (first written as 99 %; see the measurement below). The walk's own bound for what it writes into the lap record is 99.9 %, and iRacing's Next Lap has been measured landing 11 frames before the line, at 99.78 % of an 85-second lap, where the walk reports "did not converge" and records nothing (#1432). Eleven frames are noise against a 300-frame run-up, so the green fallback judges the landing by its own, looser bound and leaves the record's bound to #1432. A landing further off than that, or in another lap or session, is a search that came to nothing: the replay is put back as the press found it (see _When the search gives up_ below). Until #1432 lands, a press on such a tape searches again every time and the walk logs its warning.
- **Where iRacing's lap search puts lap 1 on a rolling start (measured 2026-10-13, one tape):** an official race at Motegi, rolling start, saved replay. Previous Lap from lap 1, and the Next Lap / Previous Lap nudge after it, rest on frame 47349, where the pole car is on lap 0 at 97.99 % of the lap and `SessionState` still reads 3. That is 68 frames before the green (47417) and about 100 before the car takes the line. For lap 2 the same searches rest at 99.90 % (Previous Lap) and 99.82 % (Next Lap), so this is not #1432's few frames: for lap 1 of a rolling start the lap search leaves a lead-in of over a second. At 99 % the fallback gave up on that landing, which would be every rolling start; at 90 % it lands on 47049, 68 frames before green minus 300, a run-up of 6.1 seconds for 5. Decided (master-c3 on this measurement, Niklas's to overrule): 90 %. The limits, stated and not engineered around here: it is one measurement on one track; an unverified landing is never recorded, so every such press searches again (7 seconds, 4 with the session map cached); and the lead-in looks like a time while the bound is a fraction of a lap, so on a lap short enough that 100 frames at pace speed is more than a tenth of it the search would still give up and put the replay back. That last case is not measured. #1436 would replace the lap search here altogether.
- **Still not verified, on a standing start:** a landing a lap search produced is trusted at 99.9 % on lap 0 like on any other lap. If iRacing's Previous Lap from lap 1 were to land on a frame of the grid wait instead of near the line, that frame would be recorded as the lap-1 start when the car reads 99.9 % there, and taken as the anchor when it reads 90 %. The rolling-start measurement above shows the search resting 100 frames before the line, which on a standing start is inside the wait on the grid; where it rests there, and what a gridded car reads, has not been measured. A standing-start replay with no record is the test, and #1436 would settle it for every lap by finding the frame where the lap counter changes.
- **A car is not on track for the whole recording (2026-10-13).** The walk bisects on the car's lap, and as first built (#607) a probe that found the car out of the world was read as "before the target". That holds before a car joins and fails after it has left: on the Motegi tape the pole sitter retired on lap 6 of 22, the first probe at the middle of the race found it gone, and seventeen jumps later the search gave up on frame 204558, five frames from the end of the recording, 44 minutes from the green. The same line was in every shipped Jump to Fastest Lap, for any car that left before the end of the tape; this spec's fallback only made it the default path. As built now, a probe that finds the car gone moves no bound, ever: bounds come only from probes that show the car, the lower one from a lap before the target and the upper one from a lap at or past it. Gone is no information, because a car is gone before it joins, after it retires, and every time it sits in the garage between two runs, and one frame cannot tell which; a rule that reads "gone, later than a frame that showed it" as "left for good" would fail in every practice session. The search takes the next frame of the open interval instead: the midpoint, then the quarter points, the eighths and so on, starting over whenever a bound moves, so a search that always finds the car probes exactly what a plain bisection would. A walk spends at most 31 such probes (five rounds of halving, which finds a car that was on track for a sixteenth of the session). When the probes run out on one that found the car gone, the lap steps start from the nearest frame that showed it. A car no probe found ends the search.
- **When the search gives up, the press leaves no trace.** Every way the walk fails after it has read where the replay was ends with the cursor back on the frame the press found it on, then the speed it had there, then the camera: a car never found, a jump or a lap search that did not settle, a session map that could not be built, a landing the green fallback will not take. Not the **Replay jump playback** setting, since nothing was jumped to. This generalises the undo the walk already had for a race the recording does not hold. The order matters and is tested: the way back is waited for on its read-back before the camera is switched, because a camera change sent while a position jump is still seeking is swallowed (measured for #1430), and the walk's give-ups can come while iRacing is still seeking. Jump to Fastest Lap gets the same, and its camera goes back to the car that was on screen when an Always My Car key had moved it. Three cases stay as they were. A cancellation by another replay command puts nothing back: that command's effect stands. A walk that never read where the replay was, or that turned out to run from the car, has nothing to put back and nothing to do it with. And a way back the sim does not honour is logged, with the replay left paused where the search stopped. Measured on the sim from a replay playing at 2x: 31 probes for a car index nobody drives, then one jump back, 2x again and the camera returned, 19.6 seconds in all.
- **A jump is waited for in proportion to its length.** The walk gave each of its own jumps a fixed four times **Fastest Lap Search Delay** (1.6 seconds at the default). A position jump's time grows with its length all the way, measured on the same tape at 165 ms for 30,000 frames, 400 for 60,000, 896 for 120,000 and 1495 for 195,000, which is iRacing's 2048 frames a sim update; a jump of about 208,000 frames outlasts 1.6 seconds, and the walk's first probe is half the session. So on a recording of about two hours the walk would give up on its first jump. The wait is now the larger of the old one and twice the jump's time at that rate, the old one staying as the floor so a user who raised the setting loses nothing. The way back, which may be sent into a seek still under way, is bounded by the length of the recording. Covered by test and by that slope, not by a run: the tape's longest jump was 195,000 frames. #1430's gate is to replace this with its own bound; it is one function (`replaySeekWaitMs`). The waits for iRacing's own searches were at first left as they were; the next paragraph is what a measurement made of that.
- **A session search is waited for by its possible length too (2026-10-13, after Niklas asked "what about a 24 hour race?").** Measured on the same tape, paused: Next Session across 8,406 frames took 78 ms and across 29,463 frames 250 ms; Previous Session from the end of the tape to the race's start, 166,094 frames, took 1366 ms, which is the long point measured for a session search and the same 2048 frames a sim update as a position jump. To Start is not a scan: 31 to 46 ms from the last frames of the tape. And on a paused replay nothing in the telemetry moves while a session search runs (frame, session, session time and state all hold; `SessionTick` runs on as it does through a no-op), so a search still under way reads exactly like one that did nothing, which is how the walk recognises the last session. With the fixed wait of four times **Fastest Lap Search Delay**, a session longer than about 55 minutes that is not the last one therefore ended the session map there, silently: a long practice, or a race in an offline event that was restarted. That was on master since #1203. As built now, a Next Session search is given the time a search to the end of the recording from where it leaves would take (`replaySeekWaitMs` of the frames to the end, the old wait as the floor) before it counts as "already in the last session". From the last session a real event lists, none is sent: an event that is not offline runs each session once, so nothing can follow. An offline event may have been restarted, which repeats a `SessionNum`, so there the search is sent and waited out; that costs up to twice the scan time of what is left of the tape, 21 seconds from the start of a six-hour last session, once per map build, and a press from outside the race builds the map every time. As a guard for a wait that still proves too short (a machine whose sim updates come slower than 60 a second), a bisection probe that reads another session than the map's bounds promise ends the walk, drops the cached map and puts the replay back; the cache is in memory only, per plugin process, and dropped on disconnect. Lap searches keep the old wait (they cover a lap), and so does To Start. Two facts for whoever reads the map code next. Previous Session from the race's first frame (37869) landed on frame 0, not on qualifying's start: that frame still carries qualifying's clock; the walk uses no Previous Session. And on a replay playing at 1x a session search does show: the frame advanced for 62 ms, stalled for 201 ms and then read the new session, while through a no-op it advanced on every tick. That stall is the better signal, and it is not used here, because the map is built on a paused replay on purpose and reading each session's first frame off a playing one is a restructure that belongs with #1430's gate.
- **Which frames a gone probe is followed by.** The midpoint first, then toward the start of the open interval (the first quarter, eighth, sixteenth and thirty-second), and only then the rest, one round of halving at a time, each round walked from whichever of its ends is nearer the last probe. A probe costs a jump whose time grows with its length, so the order is chosen for travel: a car that drove the lap being looked for and is gone now has usually retired, and the green fallback's lap is always the first. In a six-hour session a car that left in the first quarter of an hour is found on the fifth probe within one crossing of the session; plain left-to-right halving needs sixteen probes and five crossings. A car that only joined for the last sixth costs seven probes and under two crossings, and all 31 probes for a car never found travel 4.2 crossings, where left to right is six.
- **What a press costs on a long recording.** The design target is a session of four to six hours (Niklas, 2026-10-13: 24-hour races are rare, four to six hours are not). Six hours are 1,296,000 frames, about 10.5 seconds end to end at the measured rate; everything here is extrapolated from jumps of up to 195,000 frames and a session search of 166,000. With a record: one jump, up to 10.5 seconds from the far end. By search: the bisection's jumps add up to about one crossing, so about 15 seconds, and about 25 when a six-hour session has to be crossed first to reach the one being searched. A car that left early: the same 15 to 20 seconds. A car never found: about 44 seconds of probes plus the way back, a minute in all. At 24 hours it works, slowly, and nothing is tuned for it: 42 seconds per crossing, about 50 seconds by search, three minutes of probes for a car never found. Nothing on the key says the search is still working; that is a follow-up of its own, built after #1430. Any other replay key stops the search at once.
- **One known gap, accepted:** from outside the race, in a recording that holds several passes of it, the lap record cannot answer, because it takes a `sessionNum` alone only when exactly one session has it. Such a press searches the replay every time, even after a search recorded the lap under the latest pass. It needs a restarted AI event, a cursor outside the race and no recorded green at once, and the fix would change the lap record's lookup rule, which is #1203's.
- **The landing:** `lapStart − GREEN_APPROACH_FRAMES`, through the same waited jump. A walk lands two ticks before the line, so it gets one further waited jump back by the rest of the lead-in.
- **The camera:** the walk's lap search is camera-relative, so it switches the camera to the pole car (#1203). After the landing, and before playback, the camera goes back to the car the user was watching at the press. (Traced by reading, not measured: when the camera is not on the car the walk is searching for, because that switch was swallowed by a jump under way, the bisection still lands near the right lap, since it reads the target car's own lap, but the lap steps follow the car on screen. The walk then judges the target car on a frame where another car crosses the line, reports that it did not converge and records nothing: it never records a wrong lap. Jump to Fastest Lap rests there with its warning; the green fallback takes the frame only when the target car is itself within the bound of that line, and otherwise puts the replay back. Making that first switch wait is #1430's.) A record-path fallback switches no camera. When the pole car is already on screen nothing is switched at all. The camera also goes back when the walk gives up or the last jump stops short, but not when another replay command cancelled the press: that command's own effect stands, and the camera is left on the pole car. A switch back that iRacing refuses is a warning, not a stop: the replay is where the press asked, and the playback step still runs.

Why this lands close: the pole car takes the line first. In a standing start its grid slot sits just behind the line, and in a rolling start the green flies at the line. So its lap-1 start trails the green by a second or two at most, and the five-second lead-in absorbs that. It is approximate in two named cases, both accepted. A pole sitter who started from the pit lane crosses late, so the fallback lands after the green. A track whose standing-start grid sits well behind the timing line lands correspondingly early.

**The capture that confirms the model:** on a rolling start, the record holds both the green frame and the pole car's lap-1 start. Their difference must be small and positive. That also shows whether pace-lap crossings move `CarIdxLapCompleted` off −1 (#307 says it stays −1 until the first S/F crossing, but no capture of a pace lap is cited for it). If a parade crossing does open lap 1, the fallback is wrong on rolling starts. It then targets the first lap start after the race session's last `ParadeLaps` tick, and this spec is amended.

**Rejected: land at the race session's start (Next / Previous Session).** It is cheap and always works, but for a rolling start it lands minutes before the green, behind gridding and every pace lap. That does not do what the mode's name says.

**Rejected: grey the key out with no record.** Every replay that exists today has no green record, so the key would be dead on all of them, including the requester's. Replay Markers greys out because a marker is the user's own and there is nothing to approximate.

**Rejected: search the replay for the `SessionState` change.** A bisection on `SessionState` across the race session would find the green itself. But whether session-level telemetry follows the replay cursor is not established (see #1324 above), and the lap walk is already built, repaired and tested. **Measured since (2026-10-13), and now #1436:** on a saved replay `SessionState` does follow the cursor, to the frame (3 through frame 47416, 4 from 47417 on the Motegi tape), while `SessionFlags` reads 0 on every frame. A script found the green that way, exactly, with no car and no camera, where the lap search lands 68 frames early and the lap record 22. Whether it holds in a replay watched inside a live session is still not measured. It stays out of this change: it is a second search routine, and it would serve lap starts as well as the green.

## Restarts

The extension, not part of this issue: a **Next Green / Previous Green** pair over every green of the cursor's race session instance, start included. It walks relative to the cursor with Replay Markers' next/previous windows, and the key greys at the ends like a marker key, since restarts have no approximation. It joins `DIRECTIONAL_PAIRS`, which also makes it a natural rotation mode for #801's dial. Because the record already holds restarts, adding the pair is action code only. It is not offered to the requester now (maintainer, 2026-10-05); it stays here as the design the stored data was shaped for, and a later issue builds it. If it is built, the pair is what names the green; Jump to Race Start stays the start of the race and nothing else.

## The dial

Replay Control has no dial surface on `master`: both the Elgato and the Mirabox manifest declare it `["Keypad"]`, and the `onDialDown` / `onDialRotate` handlers are unreachable (#640). #1316 builds the surface (Speed Control, with Frame Jog in #1317), and #801 adds stepping modes to it.

- **No rotation mode.** A single moment has no direction to turn in. If the restart pair is adopted, "greens" becomes one more stepping target in #801's list, not part of this issue.
- **A gesture-slot option: yes.** #1316's slots (Press, Long Press, Tap Display, Long Touch) offer Play/Pause, Set 1x and play, Reverse direction, Jump to Live and None. Jump to Live already makes a jump a slot option, and Jump to Race Start is its counterpart at the other end of a race review. A Mirabox knob reaches only Press, so without the option a knob user needs a separate key for the one jump a review starts from. The cost is one enum value under `.catch`, one PI option, one comms entry and a hold-preview caption (`START`). The preview's `false` cases are the press guards above. This lands after #1316. If #1316 is not merged when this is implemented, the option goes into #1316's slot list instead.

**As built (2026-10-12, over #1433):** the gesture runs the keypad's own press through the dial's host, as Jump to Live does, so the guards, the record lookup, the fallback and the in-flight slot are the key's, and the jump takes the replay cursor itself. The hold previews `START`, and nothing in a replay with no race session or from the car; the other two guards (the unsettled tick after a seek, a jump still in flight) pass in well under the hold threshold and are not previewed. That needed one change to the dial: a gesture's preview may now answer that a release would do nothing.

## Out of scope

- The Next Green / Previous Green pair (see _Restarts_).
- A green record for practice, qualifying or any non-race session.
- Restarts after a red flag that raise no caution bit, local yellows, and the checkered flag ("jump to finish"). Each would be another `kind` or section, and the store carries unknown kinds through.
- A per-key or global setting for the lead-in.
- Recording a green seen during a replay tick, live-field or otherwise. The gate is the lap record's, and it changes with it if #1324 or a later issue changes it.
- Renaming the _Fastest Lap Search Delay_ setting, although the fallback walk now uses it too. The website paragraph says so.
- The legacy Replay Navigation action (#1334). It gains nothing.
- Ulanzi dials: none are declared until verified (`encoders-and-touchscreen.md` rule 7).

## Testing

Unit tests, in the package that owns each piece:

- **`diff/replay-greens.ts`** (sim-events-iracing):
  - The first tick seeds and emits nothing.
  - `Warmup → Racing` on a standing race session and `ParadeLaps → Racing` on a rolling one each emit one `start` with the tick's `ReplayFrameNumEnd` and `SessionTime`.
  - `Invalid → Racing` emits nothing, and neither does a practice or qualifying session going `Racing`.
  - A re-entry into `ParadeLaps` followed by `Racing` emits a second `start`.
  - A caution episode (Caution set, then `Green` rising with both caution bits clear) emits one `restart`. A green rising with `Caution` still set (yellow-checkered) emits nothing.
  - An ineligible window (in a replay by the debounced state, `SessionNum` −1, no readable frame) unseeds the recorder. The first eligible tick after it emits nothing even across a `Racing` flip, and it also clears the caution latch.
  - A session change re-seeds.
  - The diff's position in `handleTick` is pinned as pre-guard (the #1127 ordering-test shape), and the shared eligibility function has its own tests, used by both diffs.
  - A fixture cut from a capture of a race start, one standing and one rolling, replays through the diff and asserts the exact event, and the caution fixtures assert each restart. They are the `local/` captures of 2026-09-17 and 2026-09-18; a frame is made from the session time, since the watch recorded none.

- **The store's `greens` section** (replay-store):
  - A record and lookup by pair.
  - The `sessionNum` fallback picks the unique session, and of several the latest.
  - The latest start replaces an earlier one for the same instance.
  - Restarts are de-duplicated within the window and stay in frame order.
  - A newer `version` is carried through: `record` returns false and the lookup reports `newer format`.
  - An unknown `kind` and unknown fields survive a write, and `markers`, `laps` and an unknown section survive a `greens` write.

- **Replay Control** (iracing-actions, under the deck-core mock with a mocked store):
  - Target resolution: the cursor's race session, and the last race session from practice. The last race session wins in a multi-race session list.
  - With no race session, nothing is sent and the key renders unavailable.
  - A hit sends one waited `setPlayPosition(Begin, frame − 300)` (clamped at 0), then the playback step, and no camera switch.
  - A miss with a lap record jumps to the pole car's lap-1 start minus 300 with no camera switch. With no grid, it uses the viewed car.
  - A miss with no lap record walks lap 1 in the target session, takes the extra waited jump back, and switches the camera back to the press-time car before playback.
  - A walk that did not converge still lands when it left the car in the last tenth of the lap before the line, and puts the replay back when it did not. The camera goes back when the walk gives up, after the way back has landed, and stays when another command cancelled it.
  - The walk and a car that is not on track: retired before the end of the tape, not yet joined where the search first looks, gone later than a frame that showed it and back again, never present (31 probes, then the way back). Each removed behaviour turns one of these red.
  - The way back: a give-up with the seek still under way, the way back failing too, a replay command arriving during it, a speed command the sim refuses, and Jump to Fastest Lap's camera.
  - The jump wait: a probe half a six-hour race away, landing after 5.2 seconds, is waited out; one that never lands gives up and puts the replay back.
  - The session map: a Next Session search across a six-hour session that another follows is waited out (real event, and an offline event restarted after six hours); no search is sent from the last session a real event lists, and one is from an offline event's; a 24-hour race after a six-hour practice is found from near its end; a probe that reads another session drops the map and puts the replay back.

  - From the car, nothing is sent. A press during an in-flight walk or jump is ignored, of this mode or of Jump to Fastest Lap, and does not cancel the one in flight. `SessionNum` −1 ignores the press.
  - The key redraws on the tick the session list gains or loses its race, and keeps its plain look with no session list.
  - The comms catalog entry exists, `docs/reference/actions.json` lists the mode, and the icon preview's freshness test passes.

**Measured by script on 2026-10-13**, before the manual round: the action's own code, driven hands-free against the sim on a saved replay of an official road race (Motegi, rolling start, practice and qualifying before the race), with a fake deck, settings in memory and the replay store in a scratch directory. It settled the playback setting on both paths (step 1's second half), the lap-record fallback from a real 3.5-era record (step 5, landing 22 frames before green minus 300), the search fallback (step 6, as amended above), a press from qualifying (step 7), the saved-replay half of step 9 (`SessionState` follows the cursor, `SessionFlags` does not, and the recorder emitted nothing through forty jumps across the green), and a second press and a cancel during a search. It cannot record a green, so steps 1 to 4 stay manual, as do the look of the key, the dial hardware, the grey key and the live half of step 9. One fact for step 4: the lap record's frames sat about 55 frames before the same moments on the saved tape, the documented saved-replay lag.

Manual, in the sim (the gate before the PR), with the plugin's log open at debug. The steps use offline AI races, and restarting the event between steps adds a race pass to the same recording: a press inside a pass goes to that pass's green, a press from practice or qualifying to the latest one.

1. **Standing start, record path.** Run an AI race with a standing start (offline, held in memory). Afterwards, in the in-session replay, press from well after the start (more than 20000 frames away, the #1275 lesson). Expect `Jump to race start: record HIT (matchedBy pair)`, a landing five seconds before lights out with the gantry in view, and the replay left as **Replay jump playback** says (paused stays paused under the default; set Play to see the start run). Read the edge tick's debug line: the `StartGo` rising edge must be within a few ticks of the `Racing` flip.
2. **Rolling start.** The same on a rolling start: the field approaching the line, and the `Green` bit within a few ticks of the flip. In the same session, compare the recorded green frame with the pole car's lap-1 start in the lap record. The difference must be small and positive. **This is the capture for the fallback model.**
3. **Restart.** An oval AI race with a caution. Check the file or the debug log for a `restart` entry on the tick `caution.restarted` fires.
4. **Saved file.** In a hosted or official session (offline sessions write no file), save the replay, reopen the `.rpy` and press. Expect a record hit landing about six seconds before the green.
5. **Fallback, lap record.** Remove the `greens` section from a session file (or open a replay recorded by 3.5) and restart the deck host. Expect `Jump to race start: record MISS (no green); falling back to lap 1 of the pole car`, then `Jump to race start: lap record HIT (matchedBy …)`, a landing before the green from the pole car's lap 1, and the camera unchanged.
6. **Fallback, walk.** Move the session file away and restart the deck host. Expect `record MISS (no file)`, then `Jump to race start: lap record MISS (no file); searching the replay`, the walk to lap 1 of the pole car, a landing before the green, and the camera back on the car that was viewed at the press. Note whether the walk logs `walk converged` or `walk did not converge` (#1432): the press must land either way, and only a converged walk makes the next press a single jump. This is also the first time the walk is asked for lap 1, so it shows whether iRacing's lap search stops at the line that opens it.
7. **Multi-session replay.** Press from practice and from qualifying in a replay that holds both before the race: it lands at the race's green. Press inside the race: same.
8. **No race.** A practice-only or test-drive replay: the key is grey and a press does nothing.
9. **Session-level telemetry in replay.** In an in-session replay, scrub from before the green to after it with a Telemetry Display key showing `{{telemetry.SessionState}}`, and record in this spec whether it changes with the cursor. It no longer gates the feature, since the recorder's gate ignores replay ticks either way, but it decides whether a later "search the replay for the green" is possible. Then leave the replay for the car and check the log: no `Replay green` line may appear from the scrubbing or from the return.
10. **Dial** (once #1316 is in), on a Stream Deck+ and the Mirabox knob: a slot set to Jump to Race Start behaves like the key.
