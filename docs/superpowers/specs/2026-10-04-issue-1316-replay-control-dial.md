# Replay Control dial: Speed Control and Frame Jog

> **Issue:** [#1316](https://github.com/niklam/iracedeck/issues/1316), [#1317](https://github.com/niklam/iracedeck/issues/1317) · **Supersedes:** _none_ · **Superseded by:** _none_
>
> Point-in-time design record. The code and `.claude/rules/` are the truth; this is not documentation.

Replay Control gets a dial surface with two modes: **Speed Control** (#1316), a user-shaped speed ladder from reverse through pause to fast-forward, and **Frame Jog** (#1317), one frame per detent. #1316 builds the surface; #1317 adds a mode to it. The remaining rotation targets #801 once proposed (session, lap, incident, car) stay in #801 and are not designed here.

## The decision

Replay Control becomes a dual-surface action, like Fuel Service and Replay Markers (#1230): one UUID, `["Keypad", "Encoder"]` on the Elgato manifest with a committed layout, `["Keypad", "Knob"]` on Mirabox (the manifest parity test requires both, `encoders-and-touchscreen.md` rule 7), Ulanzi `["Keypad"]`. The dial logic lives in `replay-control/replay-control-dial-surface.ts` behind a small host interface, and every handler branches on `ev.action.isDial()`. Each rotation mode is a module of its own behind the `ReplayDialMode` interface (`replay-control-dial-mode.ts`): the surface owns the per-context state, the in-replay guard, the gestures and the display, and a mode owns what a turn does and what the box reads. Both issues ship in one pull request.

The action already carries `onDialDown` / `onDialRotate` with `executeDialDown` / `executeDialRotate`. They are unreachable: the manifests have declared the action keypad-only since #640. They are deleted with their tests, not adapted — they key the dial on the keypad's `mode`, which this design replaces with a dial-only `dial.mode`.

| Input | Speed Control | Frame Jog |
| --- | --- | --- |
| Rotate clockwise | one stop up the ladder (faster, signed) | next frame |
| Rotate counter-clockwise | one stop down the ladder (slower, signed) | previous frame |
| Press | `dial.pressAction`, default Play/Pause | same |
| Long press (Elgato) | `dial.longPressAction`, default Set 1x and play | same |
| Push + turn (Elgato) | a plain turn; the release fires nothing | same |
| Tap Display / Long Touch (Elgato) | `dial.tapAction` / `dial.longTouchAction`, default None | same |

The gesture slots are shared by both modes, so switching the Mode select never changes what the presses do. Every slot offers **Play/Pause**, **Set 1x and play**, **Reverse direction**, **Jump to Live** and **None**. Every long-press and touch option is also on Press, so a Mirabox knob (rotate and press only) reaches all of them (rule 2).

## The speed ladder

- **Order is signed.** The ladder runs from the fastest reverse speed through 0x to the fastest forward speed, and clockwise always moves toward +16x. From −8x, clockwise goes to −4x: slower in reverse, but "faster" on the signed ladder the user described.
- **The ladder is mirrored by construction.** The user picks **magnitudes**, and the ladder is `−m(n) … −m(1), 0x, m(1) … m(n)`. One choice cannot produce an asymmetric ladder, so there is nothing to keep in sync.
- **Every speed iRacing supports is offered** — 31 magnitudes: the slow-motion fractions 1/16 … 1/2 and the speeds 1x … 16x. **Ticked by default: 1/4, 1/2, 1, 2, 4, 8**, so the default ladder is −8x, −4x, −2x, −1x, −½x, −¼x, 0x, ¼x, ½x, 1x, 2x, 4x, 8x (maintainer's call, 2026-10-04: offer everything, preselect the described set).
- **Stored like Camera Controls' camera-group subset** (`cameraGroupSubset`): `dial.speedStops` is a map from a magnitude token in the keypad's own speed format (`parseSpeedSetting`: `"s4"` = 1/4x, `"2"` = 2x) to a boolean, and a token absent from the map reads its default. So the stored object holds only what the user touched, and a magnitude added to the offer later arrives with its own default rather than silently off. Unknown tokens and non-boolean values are ignored. A map that ticks nothing parses to the default set; that is only reachable by hand-editing, because the PI will not let the last box be cleared. 0x is always on the ladder and is not a token.
- **A stop is `{ speed, slowMotion }`**, the shape `setPlaySpeed(speed, slowMotion)` takes: −¼x is `{ -4, true }` (the keypad's Slow Motion Rewind already sends that shape), 8x is `{ 8, false }`, 0x is `{ 0, false }`. Comparison goes through one signed numeric value (`slowMotion ? sign / |speed| : speed`), so the ladder and "where am I" share one function.

## Rotation — Speed Control

- **Read the live speed, not a cache.** The current speed is `ReplayPlaySpeed` / `ReplayPlaySlowMotion` from the latest telemetry, overlaid by a pending speed: after a dial send, a pause included, the live speed reads as the sent speed until telemetry reports it or 500 ms pass (`replay-speed-state.ts`), so that two detents arriving before telemetry catches up do not compute from the same stale value. The first design relied on the action's existing optimistic `setLocalSpeed` cache alone; the next telemetry tick overwrites that cache, and that tick can still carry the old speed (amended 2026-10-12, during implementation). The pending speed is one module-level value, because iRacing has one replay speed, and the surface still updates the action's cache so the keypad's speed icons follow at once. Any other replay command drops it at once: every action takes the replay cursor before it sends, and the speed state listens for that (`onReplayCursorTaken` in `shared/replay-cursor.ts`), while the dial's own take keeps it, so a Frame Jog step still reads the pause it has just sent. A broadcast reports no status, so a send iRacing ignores, such as a speed sent while paused at the end of a saved recording, shows only as the 500 ms running out with telemetry never reporting it; one timer in the surface, which sends nothing, then redraws the dials and puts telemetry's speed back into the action's cache, because no tick follows an ignored send. Every input and that timer decide from a fresh telemetry read, and only the per-tick redraw uses the tick it was handed: the controller delivers a tick only when `SessionTick` advances, and a paused replay's telemetry can change without it (all amended 2026-10-12, from the code review and the second read). The Replay Markers dial needed a landing hold for exactly this, and this is that rule applied to speed.
- **One stop per detent and `|ticks|` stops for a fast spin, with no per-event cap** (maintainer's call, 2026-10-04: someone will spin it like crazy). The only limit is rule 3's clamp at the ladder ends, without wrapping. A wrap from +8x to −8x would throw the replay backwards at full speed, which is the one surprise a speed dial must not give. One event sends **one** `setPlaySpeed`, to the last stop reached; at an end, nothing is sent.
- **Off the ladder:** when the live speed is not a stop (a key set 3x, iRacing's own bar set 16x when 16 is not chosen), the first detent goes to the nearest stop strictly beyond it in the turn's direction. 3x clockwise is 4x, and 3x counter-clockwise is 2x.
- **0x is a stop like any other.** Turning out of pause starts playback at the adjacent stop (¼x on the default ladder), never at the remembered speed: the ladder position is the replay's actual speed. Press is the route back to the remembered speed.

## Rotation — Frame Jog

- **One frame per detent, one command per event** (amended 2026-10-12; the two models this section first named both failed the capture, see below). A single detent while nothing is under way is a frame step, `nextFrame()` / `prevFrame()`. Anything else — several detents in one event, or any turn while the last move has not read back — is one absolute jump, `setPlayPosition(Begin, target)`, where the target is the frame the last move was headed for plus the detents. Uncapped, and kept inside the recording: not below frame 0, and at the end by what was measured there — a jump lands at most 5 frames short of the last frame whatever it asks for, while frame steps reach the last frame but one. So a jump is aimed no closer than 8 frames to the end, and inside that stretch a turn is one frame step, or nothing while a move into it has not read back.
- **What iRacing does with the two commands**, measured against a paused replay on 2026-10-12 with a scripted probe (one fast machine, a 204563-frame recording; the times are that machine's):
  - A frame step moves exactly one frame, and iRacing applies one per sim update. Steps 17 ms apart or closer lose some; several sent back to back move one frame. Sent each time the previous step's frame change has been read, 60 of 60 land, at 61 frames a second.
  - A position jump on its own is exact in either mode. It lands within one or two updates when the target is near; a lone jump 60000 frames forward took about half a second, reading frame 0 meanwhile.
  - A position jump sent within about 415 ms of the landing of an earlier one is acted on only when that time has passed. Until it lands telemetry reads as if the replay had been left: `IsReplayPlaying` false, `ReplayFrameNum` 0, `ReplaySessionTime` 0, the session numbers −1. The wait is the same at every depth of the recording (354 to 372 ms after the last send at five depths). A jump that arrives meanwhile replaces the one waiting: a turn kept up for 3 s, retargeting every 60 ms, landed on whichever target was newest about every 0.4 s and exactly on the last one. The one limit seen: of two jumps 8 ms apart, the earlier one was applied.
  - **Any other replay command** sent during that wait ends the jump where it stands, thousands of frames from its target: a frame step, a lap / session / incident search, a speed that sets the replay playing, and a pause alike (a pause 170 ms into a jump, with nothing after it, left the replay about 8730 frames past its target, 3 of 3). Only another position jump is safe, because it replaces the target; a pause followed at once by a jump lands on the jump, which is why a pause looked harmless until one was the last command of a seek. A jump **relative to the current frame** (`Current`) sent during the wait is resolved from the start of the recording. Those two are the fault the first build had: its `setPlayPosition(Current, ±|ticks|)` per fast event, followed by a single step, threw the replay to 0:00.00 and on. The maintainer's own logged turns, replayed as that build sent them, ended 11 to 21250 frames off.
- **So a move is measured from where the last one was headed, and gated on the read-back** (`replay-position-state.ts`). Every step and jump records its target as the dial's pending target. While it stands the next move is an absolute jump from it, and the surface refuses a frame step whatever the mode asks. A reading that is not the replay's is never a position: with no target pending either, the event is skipped.
- **A target ends when its frame reads back from a replay in a way that can only mean the move is done**: the frame is one the replay could not have been showing anyway (not the frame the run of moves started on, not an earlier target of the run, not the frame on screen at the send), or a reading that was not the replay's has been seen since the send, which is what the whole of a jump under way reads. Without that rule a turn back onto the frame still on screen, or a fast turn ending on a frame it had stopped on, read as landed while the jump still waited.
- **The target is the dial's own, not the replay cursor's pending landing** (`shared/replay-cursor.ts`, the value Replay Markers keeps). The first cut shared it, and a visible Replay Markers key ended it one tick after every send, because a marker surface settles the landing once the replay is within a second of it, which a frame move always is: with that key's tick behaviour added to the harness, a 3 s spin lost 114 of 137 detents and the maintainer's 52 logged turns lost 9 of 26. Another action's cursor take drops the target, since the replay is no longer headed there; the dial's own cursor takes keep it.
- **Nothing but another jump is sent while a target stands.** Run against the sim, the dial's own Play 40 ms into a fast turn's second jump ended that jump about 9000 frames further on and played from there (#1275's rule, reached by spinning and pressing at once), and a pause did the same. So a non-zero speed asked for while a target stands, from any gesture or from Speed Control, is held and sent when the target has read back, which the redraw timer notices; and a pause or a speed of 0 asked for then is not sent at all, the replay being paused for the move already (a mode pauses a playing replay before it moves it, with the jump right behind the pause, and no playing speed goes out until the move has read back). It is dropped instead when the move never lands or another action's command takes the replay. While it waits it reads as the live speed, so the next input is decided as if it had gone out: a second Play/Pause takes it back (the local review caught that it was first queued again), a jog turn drops it before it moves, and a speed step walks on from it and replaces it — none of them sending a pause. The dial's own Jump to Live sent into a jump under way is the same hazard and is left to #1430 with the other searches. A Replay Markers landing is not read as a position either: a turn measured from a marker the replay had played past would pull it back by seconds. The same logged turns under this protocol ended exactly on target at three depths of the recording, as did the maintainer's whole logged minute (150 turns), fast spins both ways and random gaps.
- **No measured time is waited on** (the maintainer's direction, 2026-10-12: the numbers are one high-end machine's, and a slower one may be slower at all of it). The one clock is a give-up, 3 s against a longest measured read-back of about half a second: a target that has not read back by then is dropped, nothing is sent, and the next move is measured from telemetry or skipped.
- **A bad landing heals on the next turn, and only then.** A jump that ended somewhere else never reads back, so the next detent is sent to where the jog was headed. An unprompted corrective jump was rejected: it would move the replay with no input, could fight iRacing's own replay bar, and is itself a second position command. A cap on the frames per turn was rejected too: the size of a jump was never the fault (±10 and −12000 are exact), and a full spin is about one second of replay per second.
- **A playing replay** was not probed; the real mode was run against one. At 1x, 4x and 1/4x the first detent sent the pause and then the step, the second only a step that moved one frame, and Press resumed that speed. A step sent while the reading still shows the replay playing records no target, since it lands one frame from wherever the pause catches the replay; a jump after a pause is absolute and records one.
- **Rejected on the way:** `|ticks|` back-to-back steps (the first fallback named here) moves one frame per event; a queue of steps paced on the read-back keeps the picture moving frame by frame but trails a fast spin and needs a timer and cancel paths in the mode.
- **What a user sees in a fast spin:** the picture does not follow frame by frame. It lands on the newest target about every 0.4 s and on the exact frame about a third of a second after the hand stops, while the box shows the time of the frame the jog is heading for. A slow turn steps at once.
- **A detent while playing pauses first.** If the live speed is non-zero, the first detent sends `pause()` before the step, so the jog always ends on a still frame whatever iRacing does to playback on a frame step. That is measured in the manual test, not assumed. The pause goes through the remembered-speed tracker, so Press resumes at the speed that was playing.

## The remembered speed

- **What it is:** the last non-zero speed the replay actually played at, as `{ speed, slowMotion }`. It is updated from telemetry on every tick where `ReplayPlaySpeed !== 0` and never overwritten by a 0, so it is right whoever changed the speed: the dial, a key, or iRacing's replay bar. A non-zero speed the dial sends is recorded at once, provisionally: the next Play/Pause resumes it even before telemetry has reported it, and it stays once a telemetry sample reports it. If 500 ms pass without one, iRacing did not act on the send and the remembered speed goes back to what it was, unless a Reverse made while paused has replaced it since (amended 2026-10-12). Before any non-zero sample, it is 1x.
- **Where it lives:** one module-level tracker in `replay-control/` (`replay-speed-state.ts`), shared by both modes and every dial context, because iRacing has one replay speed. It is fed by the telemetry tick of every Replay Control context on screen, keys and dials alike, and only while a replay is on screen; a speed set while no Replay Control key or dial is visible is not seen (amended 2026-10-12). It is in memory only. A plugin restart resets it to 1x; persisting it would be a settings key for a value that is stale the moment the replay changes.
- **Play/Pause:** a live speed other than 0 sends `pause()`, which the tracker has already recorded the speed for. 0x sends `setPlaySpeed(remembered)`.
- **Set 1x and play** sends `setPlaySpeed(1, false)` whatever the state.
- **Reverse direction** flips the sign of the live speed and keeps its magnitude and slow-motion flag. When paused, it flips the **remembered** speed and stays paused, so the next Play/Pause resumes the other way. The strip's resume caption shows the flip at once.
- **Jump to Live** runs the keypad's existing `jump-to-live` path.

## Commands and the replay cursor

- **Every send, from either mode or any gesture, first calls `cancelReplayCursorOwner("dial-…")`**, exactly as the keypad's speed and transport modes do (they call `cancelFastestLapWalk`). A speed change in the middle of a Jump to Fastest Lap walk would make the walk misread its own probes. The dial never claims the cursor: every event is a one-shot command.
- **Outside a replay, nothing is sent.** "In a replay" is the controller's debounced replay state (`getReplayState().inReplay`, #1324) together with a telemetry tick; without both, rotation and every gesture are a no-op, because iRacing ignores replay commands while driving. Raw `IsReplayPlaying` is not read: it is false for about 300 ms after every seek, which would drop detents and blink the box dim after any marker or lap jump (amended 2026-10-12; the spec first named the raw flag). A replay also counts as on screen, for every mode, while a pending target has not read back or a replay-cursor claim stands: a jump under way holds the raw flag false, and a turn that keeps retargeting one shows it true for only one or two ticks in every 0.4 s. In the runs against the sim the debounced state held through 3 s spins by itself, so this is a second line, and it is bounded: it holds only for the give-up time past the last moment the debounced state said a replay was on screen, or turns made from the car would keep renewing their own target and the hold with it. Teaching the SDK's replay-state tracker about the plugin's own seeks instead, so every surface inherits one rule, is #1429.
- **All of it is iRacing API; no binding is involved.** The dial gets its own `comms-catalog.ts` entry keyed on `dial.mode`, with the gesture-slot values in the same map (the existing dial entries' pattern), all `api`, then `pnpm generate:action-comms`.

## Press gestures

Classified at release through `classifyDialReleaseForHost` with `getDualPressThresholdMs()`, as every dial does; no timer decides. On Mirabox every press is a short press (the adapter's atomic press, #1013).

- **Hold preview (#1120), Elgato only.** The long-press outcome is knowable before release, so when the hold passes the threshold the strip shows it ("► 1x", "◄ 4x", "PAUSE", "LIVE"). `onThreshold` returns `false` when the slot is None or the release would do nothing (not in a replay, no telemetry), and absent telemetry previews nothing rather than a default. The pending state goes into the render arguments and the displayed signature, and `up()` disarms before its early returns (the four traps in `encoders-and-touchscreen.md`).
- **Trigger descriptions** (Elgato) name the mode's rotation and the slot assignments, so the Stream Deck app's dial hint matches the settings.

## The display

Drawn through `dialCanvas()` / `setDialCanvas()` on every host, so the same code draws the Stream Deck+ strip and the Mirabox knob screen, via the shared `renderDialBox` with `dialAppearanceFields` (rule 5).

| | Speed Control | Frame Jog |
| --- | --- | --- |
| Label | `SPEED` | `FRAME` |
| Value | live speed, `formatSpeedDisplay` (`PAUSED`, `4x`, `-1/4x`) | the replay time as `m:ss.ss` — at 60 frames a second, every frame changes the hundredths. It is the time of the frame the replay stands on, or, while a move has not read back, of the frame it is headed for, worked out at 60 frames a second from the last reading; never the raw `ReplaySessionTime`, which reads 0 while a jump waits (amended 2026-10-12) |
| Caption | while paused: the resume speed, `► 4x` / `◄ 2x` | the play state, `PAUSED` or the live speed |
| Side marks | lit when a turn that way would change the speed, dim at a ladder end | both lit in a replay |

- **Not in a replay, or no telemetry:** the whole box dims, like the keypad's unavailable look, and shows the mode's label alone, with no hold preview.
- **The direction marks are `►` / `◄` (U+25BA / U+25C4).** The look-alike `▶` / `◀` are missing from the bundled Arimo and rasterize as empty boxes on the Mirabox knob (amended 2026-10-12).
- **Side marks on both sides:** `renderDialBox`'s `sideMarker` takes one side today. #1230 widens it to both, additively. Whichever of the two lands first does the widening, and the other reuses it.
- **Cadence:** re-evaluated on each SDK tick. The dedupe signature is built from what is displayed (label, value, caption, side marks, pending), never the raw frame, so a paused Speed Control dial pushes nothing. A playing Frame Jog dial changes its value every tick and is throttled to at most 10 pushes per second per dial (rule 6). While a step or a jump has not read back, the dials are also redrawn every 50 ms from a fresh reading, because a paused replay may deliver no tick when it lands; that timer draws and decides nothing.

## Settings

A new `dial` root object on `ReplayControlSettings`, `.prefault({})`, holding `mode` (`"speed"` | `"frame-jog"`, default `"speed"`), `speedStops`, `pressAction`, `longPressAction`, `tapAction`, `longTouchAction` and the `dialAppearanceFields` colours, each with a `.catch` to its default. A stored setting is a persisted contract (`code-review.md`, xhigh), and this change only adds optional keys under a new root: existing keypad instances parse exactly as before, nothing is renamed or removed, and no migration is written. The top-level `mode` is still parsed on a dial instance and ignored there. `dial.mode`'s enum is where #801's modes will be added.

The PI branches on the controller (`fuel-service.ejs` is the pattern) and shows the dial section only on a dial. That section has a **Mode** select (label exactly "Mode", per `terminology-and-refs.md`) offering Speed Control and Frame Jog, a **Speeds** checkbox grid (shown in Speed Control only) built the way Camera Controls' camera-group grid is, its 31 boxes ordered 1/16x … 16x, whose last ticked box cannot be cleared, the four gesture selects, and the appearance colours. Long Press, Tap Display and Long Touch are hidden where `dialExtendedGestures` is off.

## Out of scope

- **#801's session, lap, incident and car modes.** They get their own spec or an amendment of this one before work starts.
- **Asymmetric ladders.** Separate forward and reverse stop lists, or a "no reverse" toggle. Mirrored was the maintainer's call (2026-10-04); a forward-only user picks small magnitudes and ignores the reverse half.
- **Rotation acceleration** (bigger steps on a fast spin beyond the `|ticks|` walk).
- **Push + turn as a second function** (#801's shuttle/jog combo). Frame Jog is a mode of its own because push+turn exists only on Elgato.
- **Keypad behaviour.** The keypad's Play/Pause, speed walk and Set Speed are unchanged, including their 1x resume. Only the dial uses the remembered speed.
- **Persisting the remembered speed** across plugin restarts.
- **An unprompted correction after a bad Frame Jog landing, and a cap on the frames per turn.** Both weighed and rejected under *Rotation — Frame Jog*.
- **A frame-step or search key pressed while a dial jump waits.** It takes the cursor and sends into the jump, which ends it somewhere else — the same fault the dial no longer commits against itself, from outside it. One gate for every sender is #1430.
- **One in-replay rule for every replay surface.** The dial holds its own guard through its own moves; Replay Markers' side, and the tracker-level rule that would replace both, are #1429.
- **Ulanzi.** No Ulanzi dial is declared until its dials are verified (rule 7).

## Testing

**Unit (Vitest):**

- Ladder: building it from the map (absent tokens read their default, unknown tokens ignored, nothing ticked → default), the signed order, one-stop and multi-stop walks including a spin longer than the ladder, clamping at both ends (nothing sent), the nearest stop beyond an off-ladder speed in each direction, and 0x as a stop in both directions.
- Remembered speed: updated by non-zero samples, never by 0, defaulting to 1x, and shared across contexts.
- Gestures: Play/Pause both ways, Set 1x and play, Reverse while playing and while paused, Jump to Live, and None; the long-press classification with the extended-gesture flag on and off; push+turn firing nothing on release.
- Frame Jog: what one turn sends for a known, a pending and an unknown position (a step, an absolute jump from the pending landing, nothing), the clamp at both ends of the recording, and the pause-first on a playing replay. Never a relative jump, and never a step while anything is pending.
- The position state: a target standing until its frame reads back conclusively, the read-backs that prove nothing (a turn back onto the frame on screen, a stop on the way), readings that are not the replay's, the give-up, another action's cursor take against the dial's own, a fast turn's stops on the way against a landing that ended elsewhere, and Replay Markers' landing neither written, read nor able to end the target.
- The in-replay guard: holding through a pending target and a cursor claim, and not past the give-up time since a replay was last seen.
- Guards: nothing sent outside a replay or with no telemetry; `cancelReplayCursorOwner` before every send.
- Display: the dedupe signature (a paused speed dial pushes once), the hold preview's `false` cases, and the dimmed box.
- Settings: `dial` parses with `.catch` defaults; an existing keypad-only settings object parses unchanged.
- The comms catalog entry and the manifest parity test, green after `pnpm generate:action-comms`.

**Manual, in an iRacing replay**, on a Stream Deck+ and on the Mirabox knob:

- **Speed Control:** walk the default ladder end to end in both directions, check the clamp at ±8x, Play/Pause after a speed set from a key and after one set from iRacing's replay bar (the resume speed must match it), long-press to 1x, and Reverse while paused.
- **Frame Jog:** single detents both ways, then fast spins both ways for a few seconds each: the replay must end where the detents say and never at the start of the recording. With debug logging on, every turn logs the move it chose and the frame it measured from, and every move of a paused replay is logged with both frames, so the log shows which command each move followed. **The first capture failed** (2026-10-12): the replay jumped to 0:00.00 on fast turns on both hosts, which is what the measurements and the model above came from. Then one turn on a replay playing at 1x: it pauses, steps, and Press resumes 1x.
- **From the car:** every input does nothing and the display is dimmed.
